# GhostLock 研究笔记（Kirin 5.10.43 / ANA-AN00）

## 0. 如何拿内核崩溃 oops（重要！）

设备无 pstore、无 last_kmsg，但 **dropbox 会自动保存 SYSTEM_LAST_KMSG**：

```bash
# 列出条目
adb shell "dumpsys dropbox 2>/dev/null | grep SYSTEM_LAST_KMSG | tail -5"
# 读某一条（时间戳来自上面列表）
adb shell "dumpsys dropbox --print SYSTEM_LAST_KMSG 2026-08-22 01:25:46 2>/dev/null" > notes/kmsg_xxx.txt
```

已存档：`notes/kmsg_0125_auxpages_crash.txt`（789 行，01:25:46 崩溃）。

## 1. v75 崩溃根因（已修复）

- `select()` 的 fd_set 只在内核栈稳定于 select 执行期间；select 一返回，route 线程后续
  write/nanosleep 系统调用复用同一块栈，冲掉 fd_set 词。
- 现象：consumer 的 sched_setattr → PI walk 读到垃圾 waiter 词 → lock=0x99b465bfc718a800
  等 → rt_mutex_adjust_prio_chain+0x1f8 (0x19bf6c ldar w8,[x25]) 处崩溃。
- **修复（v76）**：`open_selected_fds` 把所有 set fd dup2 到**未武装 timerfd**（有效但永不
  就绪）→ select() 阻塞 500ms → do_select 只写 res_* 集合，输入 fds.in/out/ex 词全程
  稳定。`PSELECT_TIMEOUT_USEC` 改为 500000（必须盖过 ~200ms walk）。
- 验证：`pselect post-select +501ms ret=0`、`sched_setattr ret=0`、`calls=1 success=1 step=0`。

## 2. walk 触发与 [7] 写的现状

- walk 由 consumer 的 sched_setattr(SCHED_BATCH, nice=0) 触发，经
  `__sched_setscheduler → rt_mutex_adjust_pi → rt_mutex_adjust_prio_chain`。
  task 偏移：pi_lock=+0x894, pi_blocked_on=+0x8c0, prio=+0x124, dl.deadline=+0x278。
  （apc_4.0.asm 无 task+0xd0 引用——0xd0 不是华为 APC 相关字段。）
- rt_mutex_waiter 布局（华为 5.10.43）：tree_entry rb@0x00, pi_tree_entry rb@0x18,
  task@0x30, lock@0x38, qos@0x40, vip_prio@0x44, prio@0x48, deadline@0x50。
- **关键参数**：rt_mutex_adjust_pi 里 next_lock = waiter->lock（fd_set g11），
  adjust_prio_chain(task, RT_MUTEX_MIN_CHAINWALK, **orig_lock=NULL**, next_lock, NULL, task)。
  [3] 的 next_lock 检查用 x24=next_lock vs [x27+0x38]。

### 2.1 锁窗口差异（实测）
- 锁 = 0xffffff8003c6e000（empty_zero_page，镜像全零）：walk 能完成但**不执行 [7] 写**
  （RAWTARGET=mmap 测试：目标内存保持 0x4141...）。
- 锁 = 0xffffff800424d010（aux_pages，镜像全零）：walk **到达 [7] rb_erase 并崩溃**
  （DIAG=7 + target=0x10 时 rb_erase 读 [0x18] 立即 fault；真实目标时崩在 rb_erase 内）。
- 两个锁镜像内容都全零，差异只在地址本身 → 词的 qos/prio 值不同（低 32 位 = 锁地址）。

## 3. 01:25:46 aux_pages 崩溃（v76，TARGET_OFF=0x348d118=panic_on_oops）

**调用栈**：
```
rb_erase+0x78/0x344              ← 崩溃点！
rt_mutex_adjust_pi+0x1e8/0x320   ← adjust_prio_chain 被 LTO 内联（无独立帧）
__sched_setscheduler+0xd04/0x1acc
__arm64_sys_sched_setattr+0x3c4/0x514
```

**崩溃在 rb_erase+0x78**（rb_erase = 0xa07628，+0x78 = `str x9, [x8]`——颜色修复路径）。
rb_erase 叶子路径 0x70 处 `cbz x8, 0x134` 不跳 → x8（=[x0+0x8] = node->rb_right）
**非零** → 走到 0x78 str x9,[x8] 崩。words[] 里 tree_right w1=0 本应让 x8=0，崩溃证明
**fd_set 的 tree_right 词实际非零**（被污染/布局错位）。

**X27 区域内存**（dump 起始 0xffffff8023d7fc10；x27 寄存器值待确认）：
- fc10[0] = 0x140（与上次 v75 崩溃 dump 开头一致——select 结构残留？）
- fc10-fc50 大量同栈地址（0xffffff8023d7fdd0/0x23d7fd00/0x23d7fd28/0x23d7fc60/

- fca0 = 0x1（pi_pc 词？）
- fcb0-fcc8 = 0xffffff800424d010 ×4（SAFE 词 task/lock/qos/prio）
- fcd8 = 0x8000000000000000（deadline bit63 = FD_SET(319,ex) 写入）

## 3.1 01:25:46 aux_pages 崩溃的确凿寄存器事实（补）

- **X1 = 0xffffff800424cf98**（rb_erase 的 root 参数 = lock + 0x8）→ **lock = 0xffffff800424cf90**
- **lock (0x424cf90) ≠ g_fake_lock_addr (0x424d010)，差 0x80 = 128 字节**
- rb_erase 内部不用 x1（x0/x8/x9/x10/x11/x12），X1 即 root 参数 → lock 铁证
- 崩溃在 rb_erase+0x78 = `str x9, [x8]`（颜色修复路径）：0x70 `cbz x8, 0x134` 不跳
  → **x8 = [x0+0x8] = node->rb_right 非零**（words[] 里 tree_right w1=0 本应零！）
  → 0x6c 先 `str x8, [x11]`（x11 = parent 槽）写成功，0x78 `str x9, [x8]` 写无效 x8 崩
- x8 非零 = fd_set 的 tree_right 词实际非零 → **fd_set 词在崩溃时并非 words[] 原值**

### X27 dump 词（fc10 起始，每行 4 个 64 位词）
```
fc10: 0x0000000000000140(=320=NFDS!), 0xffffff8023d7fdd0, 0xffffff8023d7fd00, 0xffffff8023d7fd28
fc30: 0xffffff8023d7fc60, 0xffffff8023d7fc88, 0xffffff8023d7fcb0, 0xffffff8023d7fcd8
fc50: 0xffffff8023d7fd00, 0xffffff8023d7fd28, 0, 0
fc70: 0, 0, 0, 0xffffff800348d111(fake_parent! 目标=panic_on_oops 0x348d118)
fc90: 0, 0, 0x1, 0
fcb0: 0xffffff800424d010 ×4 (SAFE 词 task/lock/qos/prio)
fcd0: 0, 0x8000000000000000(FD_SET(319,ex) bit63), 0, 0
```
- 栈地址们（0x23d7fd00/0x23d7fd28/0x23d7fc60/...间隔 0x28）→ select 的 poll_table_entry 链
- fc10[0]=0x140=320 → 混入 NFDS（core_sys_select 的 n）→ **fd_set 区域与 select 局部/结构交错**
- 若 fd_set base=fc70：g4=fc88=fake_parent✓, g5=fc90=0✓, g6=fc98=0✓, g7=fca0=1✓(pi_pc),
  g8=fca8=0✓(pi_right), g9=fcb0=0x424d010✗(pi_left 应0), g10=fcb8=task✓, g11=fcc0=lock✓
  → **但 g11=fcc0=0x424d010 与 X1 反推的 lock=0x424cf90 矛盾（差 0x80）**
- 结论：fd_set 词在 walk 读取时与写入时不一致（偏移 0x80），或 x27 位置理解有误；
  **待办：拿到不截断的寄存器行（x27/x0/x25 真值）确认 node(x0) 与 waiter(x27)**

## 3.2 决定性实验：SAFEVAL 反推 fd_set 词布局（02:59 崩溃）

实验：GHOSTLOCK_SAFEVAL=0x5555555555555555 覆盖 SAFE 的 w8/w9 (qos/prio)。
结果（dropbox 02:59 崩溃，aux_pages 锁）：
- **x25 (lock) = 0x5555... = SAFEVAL**（x24/x3 也是）→ **waiter->lock 读取位置 = w8 (qos) 词！**
- x27 = 0xffffff8153837c90（waiter）；X27 dump 起始 = x27 - 0x80 = 7c10
- 用户 fd_set 词正确（v76d4 日志，empty_zero_page 锁不崩）：
  in[4]=fake_parent, out[0]=0, out[2]=1(pi_pc), ex[0..3]=g_fake_lock_addr, ex[4]=0(FD_SET 前)
- RLIMIT_NOFILE = 32768（n 不会被 clamp；dup2 到 fd 319 → max_fds ≥ 320 → size=40）

### 内核 fd_set 实测布局（base=bits）
- fake_parent (w0) @ 7c88 = fds.in[4] → **fds.in = bits + 8**（in[0] 在 7c68）
- w6-w9 (task/lock/qos/prio) @ 7cb0-7cc8（01:25：0x424d010×4；02:59：0x424d010×2+0x5555×2）
- 0x8000... (FD_SET(319,ex) bit63) @ 7cd8
- **[x27+0x38] = 7cc8 = w8 (qos) 词** → waiter (7c90) 的 lock 字段读到的是 w8 的值
- 01:25 无 SAFEVAL：x25(lock)=0x424cf90，但 w6-w9=0x424d010（差 0x80=128）
- 02:59 SAFEVAL：x25(lock)=0x5555=SAFEVAL → **lock 词=w8 词**

### 结论
- words 的 shift=4 与 waiter 实际位置（fd_set g5 = 栈顶-0x370）**错位约 1 词**
- waiter->lock 实际读到 fd_set 的 w8 (qos) 词（SAFE 时 = g_fake_lock_addr，但 01:25 观察到
  0x424cf90 与 0x424d010 差 0x80——仍有一层 0x80 偏移未解）
- w5 (pi_left)/w9 (prio) 的词值在 dump 里异常（w5 处显示 w6 的值，w9 处为 0）
- **修复方向**：把 PSELECT_WAITER_WORD_SHIFT 从 4 改为 5（waiter = g5），或调整 fd_set
  base 偏移（fds.in = bits+8 的来源待查——可能华为 core_sys_select/stack_fdset 改动）
- 待验证：shift=5 时 w0(tree_pc)→out[0]、w7(lock)→ex[1] 是否对齐 waiter->tree_pc/lock

## 3.3 shift 6 对齐成功（04:15 崩溃验证）

- PSELECT_WAITER_WORD_SHIFT 4→5→6。shift=6 时 X27 dump 完全对齐 waiter：
  - tree_pc=[x27]=fc90=fake_parent ✓，pi_pc=fca8=1 ✓，task=fcc0=lock 词=0x424d010 ✓
  - w9(prio)→global15→set3 超出（不写，prio 残留 0）——可接受

  但 RAWTARGET=mmap 未清零、klogctl 未写 → **walk 没执行 [7] 写**
- shift=6 + aux_pages 锁 + RAWTARGET=0x10：2s 崩溃（walk 到 [7] rb_erase）
- **锁地址影响 walk 是否到 [7]**：aux_pages(0x424d010)→到[7]；empty_zero_page(0x3c6e000)→不到
  - 两个锁镜像都全零；差异 = w6-w9 词值 = 锁地址（qos/prio/task 词不同）

## 5. 【重大突破】v76h：任意内核写达成（2026-08-22）

### 5.1 三个关键修复（缺一不可）
1. **P=0x80000 是正确 phys_load**（v76g 时 P=0 写错页）。
   - p0_data_alias 注释说"kallsyms 偏移=phys，phys_load 已烘焙进 VA"是**概念错误**：
     init_cred 文件偏移 0x34944e0 ≠ 物理；真物理 = 0x80000 + off（TEXT_OFFSET）。
   - 正确 target = data_addr(KIMAGE_TEXT_BASE+off) 在 P=0x80000 时 = P0_PAGE_OFFSET|(0x80000+off)。
   - P=0：写 [phys 0x348d118]（panic_on_oops 目标）→ die() 读 KIMAGE VA 的 panic_on_oops 仍=1 → panic。
   - P=0x80000：写 [phys 0x389fc30]（dmesg_restrict 目标）→ 清零成功。

2. **fake_parent bit0=0（红节点）**：rb_erase 颜色修复门控
   `sbfx x8, pc, #0, #1; and x10, x8, parent; cbnz x10, fixup`。
   - bit0=1（黑，旧 |1）→ x10=parent≠0 → 恒进颜色修复循环 → 读垃圾指针 → oops/panic。
   - bit0=0（红，新 &~1）→ x10=0 → 跳过修复 → rb_erase 正常返回 → walk 完成不崩！
   - 修改：main.c do_one_write_nospray `fake_parent = (pselect_custom_target - 8) & ~1ULL`。

3. **aux_pages 锁（0x424d010）**：empty_zero_page 运行时被内核写脏 → [5] trylock 旋转
   499ms → 不到 [7]；aux_pages bss 干净 → trylock 25us 瞬间成功。

### 5.2 验证结果（v76h + shift=6 + LOCKPHYS=0x424d010 + P=0x80000）
- `consumer: sched_setattr ret=0 errno=0 took=25us`（trylock 瞬间成功）
- `trylock SUCCEEDED (took=25us) - lock is zero memory`
- **klogctl before = -1 errno=1(EPERM)；after = -1 errno=13(EACCES)**
  → dmesg_restrict 被写 0：内核 printk 检查（EPERM）通过，后续 selinux（EACCES）挡读。
- 设备存活（uptime 190s+，无 panic/reboot）→ [7] 写目标正确未破坏系统。

### 5.3 稳定性问题：aux_pages 污染（v76h 第二次 run 崩 brk #0x800）
- 第二次 run（同参数）崩在 rt_mutex_adjust_prio_chain+0x14dc = 0x19d250（brk，BUG()）。
- 原因：[7] enqueue 写 [lock+0x8]/[lock+0x10]（waiters 树）→ 污染 aux_pages →
  下次 run 的 rb_leftmost=[0x424d020]≠0 且 rb_leftmost->lock≠lock → 0x19c130 b 0x19d250 BUG。
- 17:21 dump：fake_parent=0xffffff800389fc28（bit0=0 ✓），X24/X25=0x424cf90（0x80 偏移，dump 起始）。
- **单次利用无污染问题**；重复 run 需换 lock 窗口或重启。

### 5.4 RAWTARGET 教训
- RAWTARGET=0x10 / mmap：rb_erase 0x5c 读 [parent+0x10] → PAN fault（内核不能读用户页）
  → 只能验证 walk 到 [7]，不能验证写。验证写必须用内核目标（TARGET_OFF）+ klogctl/errno 变化。

### 5.5 待办

### 5.6 HKIP 检测（17:37 验证）
- 写 panic_on_oops=0 成功（oops 后无 "Kernel panic - not syncing: Oops"，
  "note: ghostlock_v76h[9503] exited with preempt_count 3"，系统继续运行）。
- 但 **华为 HKIP**（hkip-atkinfo "got a attack event"）检测到内核 oops → 上报

- **结论：不能依赖"触发 oops 验证"（HKIP 会拦）；[7] 写本身无 oops（红节点）
  → 利用路径干净（dmesg_restrict 写存活 509s+ 验证）。**
- run B（RAWTARGET=0x10 触发 0x5c oops）后 hung task → 华为安全响应。

## 6. 提权探索（v76h 之后：W2 cred=init_cred 路径）

### 6.1 已确认的能力
1. **[7] 任意 NULL 写**（dmesg_restrict/panic_on_oops 验证，稳定）
2. **[7] 非 NULL 写**：words[1] 从硬编码 0 改为 fake_right（fops.c v76o）
   → rb_erase 0x6c 写 [target] = fake_right（任意 64 位值）
   → 但 0x78 二次写 [fake_right] = pc（写值必须是内核可写地址，否则 PAN）
   → 所以只能写"内核地址值"（如 init_cred）——写字符串（modprobe_path）不可行
3. **W2 写 cred 机制就绪**：do_one_write_nospray(mode==2) → fake_right=init_cred
   → 写 [task+0x7c0] = init_cred（child 变 root）——但需可靠 task 地址

### 6.2 task 地址获取（最大障碍）
- **perf_find_task**（perf_event_open + sched_yield/getpid 负载采样）：
  - paranoid=-1（允许）✓
  - 但采样极不稳定：v76n 一次 255/256 票（0xffffff800dc60000），v76t 一次
    256/256（0xffffff8179fb0000），其余大量 0 票/1-2 票
  - 高票 = __schedule 的 prev（child 自己）；低票 = next（别的进程/死进程）
  - load 42 时采样分散（IP 各异）→ 低票

## 15. v89b 失败根因：is_own 路径验证被跳过 + v90 修复 (own-root)

- **v89b 诊断（本轮）**：try=1/2 采样 IP 带 KASLR slide 的 __schedule+0xa64（与 v88b 成功时相同分布），
  但 leak 命中**父进程自己**（IDENT own=1，votes 2/4），不是 child（v88b 是 child=1, votes=229）。
  try=3+ perf 全 0 票（该 boot 运气差）。
- **根因（代码 bug）**：COMBINE 路径 cred write 后的验证块
  `int target = is_sib ? sibling[sib_idx] : (is_child ? child : -1);`
  → is_own 时 target=-1，整个验证（含 CapEff/ROOT 检查）被跳过，直接打
  "W2 write did not produce root"。**即使父进程已被成功 root 也当失败**。
  v88b 命中 child 所以成功；v89b 两次命中父进程所以"失败"（写很可能已生效！）。
- **v90 修复**：is_own 分支直接读 /proc/self/status 的 Uid+CapEff 验证父进程自己；
  root 成功（CapEff=0x1ffffffffff 或 euid==0）→ **父进程自己跑全套 payload**
  （finit_module errno 直接打印、mount、enforce 写、kallsyms、kcore、/dev/mem pread、
  setcon）→ return 0。失败则 kill child + continue。
- **预期**：leak 命中 child 或父进程都能成功 → 成功率大幅提升（v88b 命中 child、
  v89b 命中父进程，说明每次 boot 基本都能命中自己人，只是验证逻辑之前把 own 当失败）。

## 16. v91 失败：perf ring 读到的是"最旧残留" + v92 修复 (读最新区)

- **v90 成功**（上个 boot）：try=1/2 leak 到高票系统任务（256/248），try=3 (CPU2) 命中
  child（votes=256）→ CapEff=0x1ffffffffff ROOT。但 **kill(child, SIGUSR1) 被 SELinux
  挡**（shell 域不能 signal kernel 域，EPERM 静默）→ child 卡在 pause()，parent waitpid
  阻塞 → finit_module 结果仍未拿到（v88b 其实也卡在这）。
- **v91 修复**：把 SIGUSR1 payload 提取为 do_root_payload()，child 循环改
  poll(cmd_r,'R',500ms) + geteuid()==0 自动检测（不再依赖信号）；parent ROOT 块先写
  cmd_r 'R' 再 kill（kill 失败无害）。**is_own 分支（v90）**：父进程自己 root 后直接跑
  payload（完整 stdout）。
- **v91 运行失败**：try=1/2/3 leak 到非自己人（votes 1-2），try=4-8 全 0。
- **根因（perf ring 读取）**：samples=1872 固定 = 512KB ring 容量（280B/样本），说明
  8M yield 完全溢出 ring。代码从 pos=0 (data_tail) 遍历到 head——**读到的是最旧的
  残留样本**（yield 循环开始时刻，child 刚 pin 未独占 CPU，regs 无 task_struct）。
  v88b 成功（samples=81）是残留区碰巧有效；v91/v89b 失败是残留区垃圾。try=3 有
  ip=__schedule+0xa64 x149 但 regs 无 task → 样本虽新但被跳过。
- **v92 修复**：`pos = (head > dsz) ? (head - dsz) : 0` —— 只读 ring 最新 512KB
  （yield 循环末尾，child nice -20 已独占目标 CPU，__schedule regs 含 child task）。
  理论上每次都能读到有效样本，成功率应大幅提升。
- v92 md5=45fb1ee2e62fdf618ae566846c33aac0，已 push /data/local/tmp/ghostlock_v92。

## 17. v92 失败：CPUNO setenv 在 fork 之后 + v93 修复 (先 setenv 再 spawn)

- **v92 结果**：try1/2 leak CPU0/1 系统任务（votes 256/253，perf 读最新区修复生效），
  try3-7 全 0 样本，try8 低票。CPU 全在线。

  霸占），CPU2-7 从未被正确采样。v85-v92 全有这个 bug（v85/v86/v87b/v88b 成功是
  CPUNO 0/1 恰好空闲）。
- **v93 修复**：setenv 移到 spawn_child 之前 → child 继承当前轮 CPUNO，真正 0..7 轮转。
- v93 md5=6c2c79cbc3af101b1bb1a48aed0106d7，已 push /data/local/tmp/ghostlock_v93。

## 19. v95 诊断 + v96 修复 (parent pin 到 CPUNO)

- **v95 诊断**：cur_cpu=cpun 完全匹配（CPUNO 修复生效），但 try=2-5 CPU1-4 全
  nc=0（nsamples=1872 nkern=1872）——**有 1872 个内核样本但 regs 无 4K-aligned
  task 候选**。原因：child 独占 CPU → sched_yield 走**快速路径**（无 runnable 切换
  对象）→ 不经过 __schedule+0xa64（DAIFClr 后 rq->curr 在 x13/x20）→ 采样 IP 是
  do_sched_yield 内部（regs 无 task）。CPU0 有系统任务竞争 → 完整切换 → 有候选。
- **v95 euid 诊断**：child 在 IDENT 阶段（未 root）euid=2000，正常。
- **v96 修复**：parent 在 spawn_child 后 `sched_setaffinity(0, sizeof(csp), &csp)`
  pin 到同一 CPUNO。这样 parent 在该 CPU 上 busy-poll（80M spin + yield），child
  yield 时切换到 parent → 完整 __schedule → rq->curr=child 或 parent。leak 必命中
  自己人，IDENT 区分 child/parent。is_own 分支（v90）处理 parent 情况。
- **预期**：每轮都能采到 child 或 parent，成功率大幅提升。
- **注意**：parent pin 可能被系统任务抢占（RT 线程），但每轮换 CPU 轮转。
- v96 md5=4b22e7d5908584ab7fb5d9beef6e22a5，已 push /data/local/tmp/ghostlock_v96。

## 20. v96 成功：root + finit_module EPERM + 探测读原语思路

- **v96 结果（parent pin 到 CPUNO 修复生效）**：try=3 (CPU2) IDENT child=1 命中
  child → cred write → CapEff=0x1ffffffffff ROOT！child payload 执行 → **child
  exit=1 = finit_module EPERM**（SELinux module:load 或模块签名强制）。
- **SELinux kernel 域全挡**：proof=0 con=(none) mount=0 enforce=1 kallsyms=0 kcore=0。
  setcon/mount/enforce 写/kallsyms/kcore//dev/mem 全部失败。
- **init 进程**：/proc/1/status Uid=0 CapEff=all-ones attr=u:r:init:s0；
  target_kirin_5_10.h 注释：init_task.real_cred = init_cred（active cred 可能不同）。
- **新思路（探测读原语）**：用 rb_erase mode=3 把 root child 的 cred 指针
  [child_task+0x7c0] 写成任意地址 X，然后 /proc/<child>/status 的 Uid/euid 字段
  显示 [X+4]/[X+0x14] —— **间接读内核内存**！流程：
  1. is_own 时 parent_task 已知 → 写 child cred 指针 = parent_task+0x7c0 →
     status 读出 parent 的 cred 指针（64 位拼接）。
  2. 写 child cred 指针 = parent_cred+0x74/+0x78 → 读出 [parent_cred+0x78] =
     **shell 域 security blob 指针**。
  3. 写 [init_cred+0x78] = shell_blob → child（cred=init_cred）变 **shell 域 +
     root** → 文件权限可用 → 装 KernelSU。
- **风险**：写 cred 指针为无效地址 → child 崩溃 → HKIP panic（设备重启）；
  探测多窗口可能超 aux_pages 限制（+0x0F00）。

## 21. v97：探测读原语实现（shell 域 blob 改写）

- **目标**：把 root child 的 security 从 kernel 域改成 shell 域 → 文件操作可用。
- **实现**：
  1. probe_read32_uid(pid, carrier_task, addr, wbase, &out)：用 rb_erase mode=3
     写 carrier 的 cred 指针 [carrier_task+0x7c0] = addr-4，然后 /proc/<pid>/status
     的 Uid 字段 = [addr]（32 位）。每 probe 一个窗口。
  2. COMBINE 分支 is_child && w2t<=4 时：读 [child_task+0x7c0]（child 原始 shell
     域 cred）64 位拼接 → 读 [ch_cred+0x78]（shell blob）64 位拼接。
  3. 写 [init_cred_alias(0xffffff8035144e0)+0x78] = shell_blob（mode=3）。
  4. 之后正常 cred write（child cred = init_cred）→ child = shell 域 + root。
- **窗口**：IDENT 0x000，probe 0x180/0x200/0x280/0x300，blob write 0x380，
  cred write 0x100（保留）。w2t<=4 时不超 +0x0F00。
- **风险**：probe 写错地址 → child 崩 → HKIP panic（设备重启）；probe 读到垃圾
  值 → 检查 linear map 范围 + 对齐后跳过 blob 改写（回退 kernel 域）。
- v97 md5=4402636b494b7e5f33126b8864b5672a，已 push /data/local/tmp/ghostlock_v97。

## 22. v97/v98 panic 根因 + v99 安全重设计

- **v97 panic**：probe 读 child 的 active cred [child_task+0x7c0]——但 probe 写
  本身就改 [child_task+0x7c0]（rb_erase 0x6c 先写 NULL 到 [parent]/[parent+8]，
  case-2 写 [parent+0x10]=[child_task+0x7c0]=fake_right）——读到的是写入后的值
  （垃圾）→ ch_cred 垃圾 → blob 探测写/读垃圾地址 → child fault → HKIP panic。
- **v98 panic**：改读 real_cred [child_task+0x7b8]——但 0x6c 写 [child_task+0x7b8]
  = NULL（parent=(target-8)&~1，parent+8=child_task+0x7b8）→ 读 NULL → ch_cred
  无效 → 应跳过，但仍 panic（可能 probe 写 [child_task+0x7c0]=child_task+0x7b4
  后 child 某处访问出问题，或 log 被恢复机制清空看不到）。
- **关键机制**：cred write（mode=2 target=task+0x7b8 leaf=1）的副作用：
  0x6c 写 NULL 到 [parent](task+0x7b0) 和 [parent+8](task+0x7b8=real_cred)；
  case-2 写 [parent+0x10](task+0x7c0=active cred)=fake_right(init_cred)。
  **active cred 变 init_cred，real_cred 变 NULL**（v85-v96 child 活得好好的，
  NULL real_cred 被内核容忍）。
- **v99 安全重设计**：载体 = **parent**（不是 child）！parent 在 spawn_child
  **之前** perf_find_task 自采样拿 g_parent_task（child 不存在，rq->curr 是
  parent 或系统任务，绝不是 child）→ 探测 parent 的 cred 指针 [g_parent_task+0x7c0]
  和 blob [pcred+0x78] → 写 [init_cred_alias+0x78]=shell_blob。child 的 cred 在
  最终 cred write 前完全不被碰 → 不 panic。每个 probe 值范围检查（linear map +
  对齐），无效则跳过。
- **注意**：perf_find_task 返回值可能是系统任务（kernel 域 blob）→ 写后无变化
  （安全但无效），下轮换 CPU 重试。
- v99 md5=930d17621125dc833497751629e62821，已 push /data/local/tmp/ghostlock_v99。

## 26. v103 崩溃根因 + v104 avc_denied patch 方案（2026-08-24）

- **v103 崩溃根因**：v103 是**第一次真正执行 probe_read32_uid**（v97/v98 两次

  - 风险：avc_denied 在 .text，华为若 text RO → fault → HKIP panic
